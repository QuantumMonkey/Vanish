## Lessons worth carrying forward (in addition to the two in 2026-08-08)

- **A checkbox's own DOM state is not proof the model state it represents has
  actually persisted.** `bim` looked like it might be an Audit-Mode write
  block at first glance (it wasn't -- `set-settings` isn't gated); the real
  mechanism was a plain async race between an instant native UI update and
  an awaited IPC round trip. Checked the gating hypothesis against the code
  before accepting it, rather than assuming the more dramatic-sounding cause.
- **A raw subprocess error string is never a stopping point for a caught
  exception.** `runPowerShell`'s reject message had been forwarded verbatim
  to the UI for as long as the function existed; nothing about the missing-
  file case was special until it was named specifically as a distinct,
  recoverable condition (`ENGINE_MISSING`) instead of one more case of "the
  process exited non-zero."
- **Before live-launching a real build, read its persisted state first, not
  after.** The second session's live portable-exe timing test triggered a
  real auto-elevation launch because the operator's own saved
  `startupMode: "full"` setting was never checked before `Start-Process`.
  Reading `settings.json` first would have predicted this exactly; reading
  it only afterward, to explain what had already happened, is the same
  investigation done one step too late to prevent the side effect.
- **This agent's own shell has no authority over processes it spawns via a
  packaged app, regardless of that app's own elevation state.**
  `Stop-Process`/`taskkill` both returned Access Denied against Vanish
  processes launched moments earlier by this same session, elevated or not.
  Do not assume a process you started can be cleanly killed later from the
  same tool context; if live-launching a real GUI app is genuinely
  necessary, plan for the case where cleanup requires the operator, not just
  hope it will not.

### Lessons worth carrying forward (beyond those already listed above)

- **A bug report's symptom is evidence; its stated mechanism is a
  hypothesis.** Three of this session's reports named a mechanism confidently
  and were wrong about it (`ri6`, `vej`, `3nd`). Reproducing before touching
  code changed what got fixed in all three -- otherwise the work would have
  been widening a sidebar that was not too wide, re-rendering detail that was
  already rendered, and "fixing" a sampling interval working as designed.
- **A green suite says nothing about surfaces the suite never opens.** An
  entire tab was dead under test at 371/371 passing. Before treating a test
  count as UI coverage, check which screens are actually reached.
- **When a measurement says a change you have good reason to believe in did
  not work, suspect the measurement first.** Three false negatives this
  session: measured `thead` instead of the `th` sticky actually applies to,
  took one before/after pair where the value settles, and measured a width
  across a CSS transition added earlier in the same session.
