## What happened today

Operator reviewed the running app (screenshots, live use) and reported seven
issues in one message. All seven were triaged, five got code fixes, two were
product/UX questions that got a recorded decision instead of a change.
Full detail in `CHANGELOG.md` under "seven operator-reported issues from a
live session". One line each:

- **`ytv`** -- UAC diagnostics. `Check-AdminStatus` used to only report
  whether the CURRENT process is elevated, which cannot tell a real UAC
  decline apart from an account that was never an administrator, or a
  machine where UAC is off. Added `Get-UacDiagnostics` (EnableLUA registry
  read + `Get-LocalGroupMember`-based group check, independent of the
  calling process's own filtered token) to `scanner.ps1`, threaded a `cause`
  (`declined` / `not-admin` / `uac-disabled` / `unknown`) through
  `relaunch-elevated` and `main.js`, and the renderer now shows a
  cause-specific message instead of one generic banner.
- **`7d8`** -- System Overview cards were wrapping to a second row even on a
  maximized window; the grid's minmax bounds needed up to 1610px for all 6
  to share a row. Lowered to 150-220px (needs ~950-1310px instead).
- **`zl4`** -- Added Clean All next to Scan All: purges every removable
  finding in every already-scanned System Clean section behind one
  aggregate confirmation, with a typed CLEAN gate if any selected item is
  `Advanced`-risk (mirrors the existing untrusted-uninstaller warning
  pattern). Tier-locked in Audit Mode like every other destructive control.
- **`bim`** -- The "Always start with administrator rights" toggle's info
  text ("Next start: ...") only updated after the settings-save IPC round
  trip resolved, while the checkbox itself flips instantly and natively --
  a real race window where a screenshot could catch the two describing
  different states. Fixed by applying the text synchronously on the
  toggle's own `change` event.
- **`frr`** -- A portable-build temp-extraction race could leave
  `scanner.ps1` missing, and Task Manager showed the raw "PowerShell exited
  with code 4294770688..." text verbatim. `runPowerShell()` now checks the
  file exists before spawning at all, offers a one-time native "Restart
  Vanish" dialog that re-extracts cleanly (same `PORTABLE_EXECUTABLE_FILE`-
  safe relaunch path `attemptElevatedRelaunch` already uses), and no longer
  passes raw stderr/exit codes into any renderer-facing error message on any
  code path.
- **`k87`** (Audit Mode write-attempt UX) and **`3ri`** (About page
  disclosure) -- reviewed, no code change. `guardFullMode()`'s toast plus
  `data-destructive` tier-locking already explain a blocked write outside of

## Lessons worth carrying forward (in addition to the two in 2026-08-08)

- **A checkbox's own DOM state is not proof the model state it represents has
  actually persisted.** `bim` looked like it might be an Audit-Mode write
  block at first glance (it wasn't -- `set-settings` isn't gated); the real
  mechanism was a plain async race between an instant native UI update and
  an awaited IPC round trip. Checked the gating hypothesis against the code
  before accepting it, rather than assuming the more dramatic-sounding cause.
- **A raw subprocess error string is never a stopping point for a caught
  exception.** `runPowerShell`'s reject message had been forwarded verbatim
  to the UI for as long as the function existed; nothing about the missing-
  file case was special until it was named specifically as a distinct,
  recoverable condition (`ENGINE_MISSING`) instead of one more case of "the
  process exited non-zero."
- **Before live-launching a real build, read its persisted state first, not
  after.** The second session's live portable-exe timing test triggered a
  real auto-elevation launch because the operator's own saved
  `startupMode: "full"` setting was never checked before `Start-Process`.
  Reading `settings.json` first would have predicted this exactly; reading
  it only afterward, to explain what had already happened, is the same
  investigation done one step too late to prevent the side effect.
- **This agent's own shell has no authority over processes it spawns via a
  packaged app, regardless of that app's own elevation state.**
  `Stop-Process`/`taskkill` both returned Access Denied against Vanish
  processes launched moments earlier by this same session, elevated or not.
  Do not assume a process you started can be cleanly killed later from the
  same tool context; if live-launching a real GUI app is genuinely
  necessary, plan for the case where cleanup requires the operator, not just
  hope it will not.
