## 1. Operator-reported defect -- unfixed, and it is a symptom

**D-1.** In the uninstaller flow, when a post-uninstall scan finds **no
leftovers**, "Move to quarantine" still behaves like a **Next** button --
it advances the wizard, on a screen that has no Next button and nowhere to
advance to.

**D-2.** The operator's second report, and the more important one: *"the app
doesn't feel modern, advanced or futuristic."* His stated intent is that
Vanish be his standing support system for this and future machines --
depended on, smooth, free of exactly this class of error.

Do not fix D-1 as a one-line guard. It is a symptom of the structural
problem below, and patching it leaves the class intact.

## 2. The structural problem, measured

`scanner.ps1` is **7,870 lines** -- **41% of all production code in one
file**. `renderer/audit.js` (1,675) and `renderer/queue-clean.js` (1,159)
are doing view *and* flow control.

When scan, classify, decide and report share one scope, **a zero-result case
has no distinct type**. Callers cannot branch on it, so the UI guesses. D-1
is that guess.

### The seam -- the prerequisite for everything after this
1. **Finders** -- one per finding type. Each returns a typed result set that
   includes an **explicit empty result**. They only find.
2. **Deciders** -- consume typed results, apply policy (safe / needs
   confirmation / never), and compute **rebuild cost**.
3. **UI** -- renders states. A zero-finding state is a *named terminal
   state*, not a step that happens to be empty.

This makes D-1 unrepresentable rather than fixed, and it is the precondition
for D-2 -- "modern" comes from a UI that always knows which state it is in,
not from styling. **Seam first, visual pass second.**

**Rules as data.** Vanish already reads CleanerML. Every finding below should
be a rule file, so a new artifact type is a data change, not a change to a
7,870-line file.

## 3. What to build -- four modules, all evidence-backed

Sequence deliberately: **Module 3 before Module 1. Rescue before reclaim.**
A tool that cannot yet delete anything but can tell you what a delete would
destroy is already the most useful thing on the machine. Dependence is earned
by knowing what not to touch.

### Module 3 -- RESCUE (build first)
Runs before any destructive action. **No competitor has this.**

- **Local-only credential scan.** Files that exist on disk, are gitignored,
  and are therefore on no remote: `key.properties`, `.env.local`, `*.jks`,
  `*.keystore`, `.playwright_session`. On this machine that was **two
  keystore passwords existing nowhere else in the world**, inside folders a
  delete-and-reclone would have destroyed.
- **Gitignored-and-unique**, generalised: for any repo, list what the remote
  does not have. That set is the true blast radius of "just re-clone it".
- **Content-hash dedup across trees**, with a survivor manifest. Used twice:
  41 duplicates inside phone backups, 79 files duplicated between two trees.
- **Every destructive action writes a manifest** -- what was removed, and the
  path of the identical copy that survived.

### Module 2 -- HYGIENE (build second: cheap, high signal, zero risk)
Finds wrongness, not waste.

| Check | Found on this machine |
|---|---|
| PATH: cross-scope duplicates, broken entries, entries under `Downloads` | 27 user entries, **12 verbatim duplicates** of the machine PATH, 2 tools running from `Downloads`. After: 14 entries |
| Redirect variables unset | `GRADLE_USER_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `npm_config_cache`, `PIP_CACHE_DIR` **all unset** -- every dev tool had silently defaulted to C: since the machine was built. This single finding explained most of the C: bulk |
| Repo health: dirty, unpushed, **unreadable** | 10 repos returned `dubious ownership` from a previous profile SID |
| Orphaned `ProfileList` entries | 12 |
| Duplicate app installs, both on PATH | 2.4 GB (one pair was intentional -- see Safety) |

### Module 1 -- RECLAIM (build third)
Detect by **project marker**, never by folder name. Only propose deleting
`node_modules` when the `package.json` that regenerates it is visible.

| Finding | Detect by | Evidence |
|---|---|---|
| Node artifacts | `package.json` -> `node_modules`, `.expo`, `dist`, `build` | **23 GB in one repo, 614 MB after reinstall -- 37x cruft** |
| Flutter/Dart | `pubspec.yaml` -> `build/`, `.dart_tool/` | 5.6 GB |
| Gradle/Android | `gradlew` -> `.gradle/`, `android/app/build/` | 5.8 GB |
| Package caches | known paths per tool | npm 4.5 GB, Gradle 14.7 GB, pip 570 MB |
| Orphaned VM images | `wsl -l -v` + age + no user files inside | **12 GB**, cold 6 weeks, contained no source |
| Redundant archives | `*.zip` beside an extracted dir of the same name | 1.8 GB |
| Installers for installed software | filename matched to registry `DisplayName` | 1.2 GB |
| Windows standard | Recycle Bin, `%TEMP%`, Update cache, WinSxS via DISM | 22.32 GB component store, 14 reclaimable packages |

**Every proposal must state its rebuild cost** -- "`npm install`, ~2 min" vs
"re-download 12.9 GB". That number decides, not the size.

### Module 4 -- REPORT
One artifact per run: *"You can reclaim X GB. Here is the breakdown, the
rebuild cost of each, and the N things that are wrong but free."*

## 4. Design constraints that are not negotiable

**The verification discipline.** This session produced **five** instances of
one defect class, and this tool deletes things for a living:

> *A check that cannot distinguish "clean" from "could not read" will happily
> authorise deleting work.*

The five: git ownership errors read as clean; `[ -d ]` on a case-insensitive
filesystem reporting renames already done; an unquoted search path silently
skipping an entire store; `$?` after a pipe scoring `tail` instead of the
command (**twice** -- the second immediately before an `rm -rf`); and a
permission-denied restore-point query reported as "disabled".

Therefore, binding:
1. **A finder must distinguish `found nothing` from `could not look`.** Three
   states, never two. `could not look` must never reach a decider as empty.
2. **A destructive step must verify its own precondition by comparison,
   inside the code, immediately before acting.** `cp && rm` is not enough --
   compare counts and bytes.
3. **Never offer an irreversible action dressed as a reversible one.** This
   is already the `z3s` / `7v3` precedent: the installer cache ships
   audit-only rather than offering a removal the vault cannot undo. Hold that
   line for every new cleaner.

**Safety cases already learned:**
- Two Antigravity installs looked like duplication and were **intentional**
  (agentic IDE + VS Code fork; one is needed to install BMAD). Never
  auto-flag same-name installs as redundant without asking.
- The Flutter SDK looked orphaned and was **not** -- SplitSmart is a Flutter
  app. Detect consumers before calling a toolchain unused.
- `C:\inetpub` looks like an unused IIS leftover and is a **CVE-2025-21204
  mitigation**. Deleting it weakens the machine. Hard-code it as never-touch.

## 5. Scope position (do not relitigate)

Vanish remains **KILLED commercially** (LED-014). Nothing here reopens that.
P2 (incumbent-patchable) and P6 (no bait without a hook) both stand -- adding
cleaners walks toward CCleaner and BleachBit, which is exactly why it was
killed. What changed is that it now has a real specification derived from
real usage.

Build it as **the operator's personal machine-hygiene suite**. That is the
sanctioned scope. The defensible slice is the developer-specific half, which
no consumer cleaner will implement, because their user does not have a
`pubspec.lock`.

## 6. What this will not do

It will not make a machine reset unnecessary in general. It did here -- C:
122 GB -> 291 GB free, no format -- because the machine was *disorganised*,
not rotten. No tool fixes a corrupted profile, a broken update chain, or
driver damage. What it removes is "slow and full" as a reason to reformat,
which is why most reformats actually happen.
