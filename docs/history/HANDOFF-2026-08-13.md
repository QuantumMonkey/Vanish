## What was actually wrong, after four sessions of looking

The elevation "loop" was never an elevation problem. From the operator's real
oplog:

```
04:35:50  relaunch-deelevated  outcome=success   (clicked Restart now)
04:37:20  app-start            tier=FULL         <- came back elevated
04:37:29  relaunch-deelevated  outcome=success   (tried again)
```

No `relaunch-elevated` entry exists that day at all. **De-elevation was
failing.** The app never reached Audit Mode, so there was nothing to
re-elevate, and the "Restart as administrator" button was never on screen --
it does not render in Full Mode. Every previous description, including the
operator's "it didn't re-elevate" and my own framing, described a symptom one
step downstream of the fault.

The cause was a success criterion, not a mechanism: the engine ran
`Start-Process runas.exe` **without `-Wait`** and returned success the moment
the process existed. runas then ran, and whatever it decided went to a console
window that closed. Its exit code was never read.

Fixed in `6162ae6`: the engine waits, reads the exit code, captures stderr; the
relaunch marker records its **direction** and the next boot compares where it
landed against where that direction intended to go. `6lg` only ever asked about
the elevate direction, which is exactly why two failed de-elevations produced
no evidence anywhere.

**Shipped detection, not a proven mechanism fix.** Whether
`runas /trustlevel:0x20000` actually drops privilege on this machine is still
unproven. The environment is already ruled out: `seclogon` Running,
`EnableLUA=1`, `ConsentPromptBehaviorAdmin=5`, manifest `asInvoker`,
`startupMode=audit` (so the startup auto-elevate path, which requires `full`,
did not fire).

## A wrong answer worth reading, because it produced a feature

The operator asked what `rpdsvc` was, with 54 open connections. I said Remote
Desktop Services, all loopback, nothing leaving the machine. They pushed back:
*"what if i dont use microsoft remote desktop at all... this feels like a
vulnerability waiting to be exploited."*

They were right and I was wrong on both counts:

- `rpdsvc.exe` is **RealTimes Desktop Service** (`ProductName`, `CompanyName:
  RealNetworks, Inc.`, `FileVersion 25.0.0.316`), shipped with RealPlayer. It is
  not Remote Desktop. `C:\Program Files (x86)\Real\RealPlayer\RPDS\Bin\rpdsvc.exe`,
  running as **LocalSystem**, **Auto** start.
- Actual Remote Desktop is **disabled** here (`fDenyTSConnections=1`), which is
  what made their instinct correct.
- The 54 established connections *are* loopback. But the service is also
  **listening on `0.0.0.0:20121` and `[::]:20121`** -- every interface. I
  conflated "the conversations it is having" with "who is allowed to start
  one".
- **The binary is validly signed** -- `Get-AuthenticodeSignature` Status=Valid,
  `CN=RealNetworks LLC, O=RealNetworks LLC, Seattle WA`, EV certificate
  (`Private Organization`). This should have been checked BEFORE saying
  anything alarming about a SYSTEM-level listener. Signed means **authentic,
  not safe** -- the exposure is real either way, and both facts have to be
  shown together or the feature is either reassurance theatre or scaremongering.

The product gap behind the wrong answer is filed as **`ddx`**: Vanish's network
panel answers *who is this program talking to* and never *who can start a
conversation with this program*. The second is the security-relevant question
and it is invisible today. A LocalSystem service belonging to software the user
does not use, accepting inbound from anywhere on the network, is precisely what
this app should point at -- and Vanish was showing the reassuring half of that
picture while hiding the alarming half.

Filed P1. The honest claim is "this is reachable", never "this is unsafe".

A second correction followed, and it is the more important one. I had also
told the operator "RealPlayer installed 2025-12-28". The registry `InstallDate`
for that entry is **empty**; `20251228` belonged to the adjacent RealNetworks
VC++ Runtime rows, and `2025-12-28 16:13` is the binary's file timestamp, not
an install record. The date was plausible. The sourcing was not, and on a claim
about admin-level exposure those are not the same thing.

Auditing our own code for the identical move found it immediately:
`scanner.ps1` falls back to the uninstall **key name** for an install date when
a program recorded none -- a defensible, properly guarded heuristic -- but both
render sites show an inferred date exactly like a recorded one. The app presents
an inference with the confidence of a measurement. Filed as **`c0y`**. It is the
same discipline `bu2` already enforces with owned/orphaned/unattributed, simply
never applied here.

## A standing rule was amended, deliberately

Rule 6 forbids a trusted-publisher allowlist. The operator has authorised one,
**scoped to grouping startup items only** (`tda`):

> we can trust microsoft, antivirus solutions, and highly vetted + necessary
> third party software killing which could compromise the computer's use.

And the case that makes the feature worth building:

> this is not useful in personal cases, but is necessary for corporate/
> enterprise machines where they install legalised spyware to monitor their
> employee's activities.

On a managed machine the monitoring agent is exactly what an employee must
**not** disable -- not because it is benign, but because disabling it is a
disciplinary event. So "necessary" must never render as "trusted" or "safe".
Wording like *"Managed by your organisation"* or *"Your system depends on
this"* carries the real claim.

`rpdsvc` is recorded in that issue as the counter-example that keeps it honest:
it runs as LocalSystem and would pass a naive "necessary" test while being
unused software listening on every interface. **LocalSystem is a weak signal,
never sufficient alone.**

When implementing, mirror the amendment into `docs/promptgate.md` Rule 6 with
its scope limit stated, so a future session does not read it as general
permission.

## Two tooling traps that cost real time

1. **The working tree is CRLF** (`core.autocrlf=true`) **and
   `renderer/core.js` carries an embedded UTF-8 BOM mid-file** from the
   renderer split. Exact-string edits fail silently against `'  }\r'`, and any
   read-modify-write that does `split`/`join` normalises the whole file into a
   2,200-line diff. Patch those files with a **surgical raw-string splice**:
   locate the substring by index, rebuild using the file's own EOL, splice.
   Never `split`/`join`.

2. **A source-vs-asar diff is not sufficient verification.** Boot the packaged
   app from `dist/win-unpacked/resources/app.asar` with the stub preload and
   assert cross-module functions resolve with a clean console. That is what
   catches a file that exists in source but was never packaged -- the exact
   failure the renderer split introduced via `package.json`.
