## The one decision waiting on the operator

**`z3s`'s open half.** The vault refuses to restore into protected system
locations (`%SystemRoot%` and friends). That guard is now symmetric - quarantine
refuses to TAKE what restore would refuse to give back, which was a real bug
where a purge from such a location stranded the file permanently.

The consequence is that `7v3` (orphaned Windows installer cache) ships
**audit-only**: 137 MB identified on the dev machine and unclaimed, because
offering the removal would be a deletion with no way back dressed as a
reversible one.

Unlocking that space means deciding whether a restore to a file's own **recorded
original path** may write into a protected location. It is arguably safe - a
restore to where we took it from is not an arbitrary write - and it is the only
route to that 137 MB. It is a security-boundary call, deliberately not made
without the operator.

## Facts about this machine and the sandbox that cost time to learn

1. **Windows Sandbox: closing it discards everything; restarting Windows FROM
   INSIDE it does not.** So a UAC change made in-guest survives an in-guest
   restart. Operator-confirmed 2026-08-19, after this was claimed to be
   impossible and was not.
2. **The Sandbox image ships with UAC OFF** (`EnableLUA=0`) and its account is an
   administrator. With UAC off the app is always Full Mode and the Audit Mode
   banner never renders, which is why `69a`/`adg` need UAC turned on there first.
3. **The host's UAC is currently ON** (`EnableLUA=1`,
   `ConsentPromptBehaviorAdmin=5`, `PromptOnSecureDesktop=1`), so elevation
   prompts on the secure desktop and cannot be driven from a tool call. Earlier
   in the session it was 0 (silent), which is what allowed the automated elevated
   runs. If a session needs silent elevation again, that value is the switch -
   and it is the operator's to change, not ours.
4. **`test/logs` is per-machine now** (`test/logs/<COMPUTERNAME>/`). It used to be
   flat, and because Sandbox maps the repo read-write, a host `npm test`
   overwrote the VM's failure logs mid-diagnosis. Do not run `npm test` on the
   host while a sandbox run's logs are still needed.
5. **A fresh Sandbox shell needs two things before npm works**: node on PATH
   (`$env:Path = 'C:\Users\WDAGUtilityAccount\Desktop\nodejs;' + $env:Path`) and
   either `npm.cmd` or `Set-ExecutionPolicy -Scope Process Bypass -Force`,
   because a bare `npm` resolves to `npm.ps1` under a Restricted policy.
6. **The repo moved** to `D:\quickhelp\vanish-uninstaller` (no space). Every
   memory or comment naming `D:\quickhelp projects\` is historical. The spaced
   path quoting must stay - the sandbox mapping still has a space by design.

## The recurring defect class in this codebase, worth internalising

Six findings in two days were the same shape: **something reported an answer
confidently, and the answer was not about what it claimed.**

- An audit-trail assertion read an oplog frozen on 3 August, passing while the
  purges it had just performed went to a file it never opened.
- A tooltip test passed unelevated for a reason unrelated to tooltips, because
  the Audit branch supplies its own text.
- Install dates read US-first on a day-first machine, putting impossible future
  dates at the top of a list sorted by date.
- A harness tested the engine while its assertion text claimed the vault.
- Two static source checks accused correct code; both times the regex was the
  defect.
- A sandbox booted into nothing and Windows reported the malformed config
  nowhere.

When something passes, ask what would have to be true for it to pass *wrongly*.
