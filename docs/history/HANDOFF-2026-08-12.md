## The elevation-loop mystery -- read this before touching elevation code again

Live sandbox testing surfaced an intermittent bug: clicking "Restart as
administrator" would sometimes close and reopen the app, but the new
instance came back in **Audit Mode**, not elevated -- no crash, no visible
error, just a loop with nothing to explain it.

**Investigation so far:**
1. First reproduction: worked once (`kt0` pass), failed on a second
   attempt in the same sandbox session with **no UAC prompt at all**.
2. Isolated with a raw PowerShell command (`Start-Process -Verb RunAs`,
   completely outside the app) -- **also failed identically**, which read
   as strong evidence this was a Windows Sandbox (WDAG) environment issue,
   not app code.
3. **Operator correctly pushed back**: one PowerShell test isn't proof
   against an app-side bug, especially given their own repeated experience
   was that the failure tracked using Vanish specifically. Re-read
   `Check-AdminStatus` (scanner.ps1) and `runPowerShell`'s spawn mechanism
   (main.js) -- both look correct on inspection, but that is not the same
   as proof.
4. **Landed on**: rather than keep arguing from an inconclusive data
   point, instrument the actual code (`6lg`, committed `80e089f`). The
   next time this loop happens -- in the sandbox, or anywhere else -- the
   very next launch will show an explicit toast and log a
   `relaunch-elevated-mismatch` oplog entry with a full UAC diagnostics
   snapshot, giving a definitive yes/no on whether Vanish's own relaunch
   attempt actually succeeded at the OS level.

**Next session, if this recurs**: check the oplog
(`%APPDATA%\vanish\vanish-state\oplog.jsonl` or wherever Settings' "Open
data folder" points) for `relaunch-elevated-mismatch` entries, and read
the toast text on the affected launch. That is now real evidence instead
of another guess.

**Separately, operator direction on the underlying model** (2026-08-11,
not yet implemented, worth reading before any further elevation work):
"admin = elevation, audit = no elevation, the toggle itself triggers uac
if needed and not disabled, otherwise moves on as admin if there is no uac
prompt because it is disabled" -- this matches CURRENT actual behaviour
already (`Start-Process -Verb RunAs` already does exactly this; confirmed
live). The one real, not-yet-built ask inside that message is filed as
**`qyt`**: distinguish "UAC is off, and you could turn it on" from "UAC is
off/locked by domain Group Policy, common on corporate machines" -- see
that issue's design notes for a concrete, honestly-caveated detection
approach (no clean single registry flag exists for this; the design notes
work out the best achievable heuristic).

## Lessons worth carrying forward (this session's additions)

- **Do not trust a privilege-drop/privilege-change mechanism without a
  live elevated test.** `dtd`'s v1 (`Shell.Application`) looked correct on
  paper, passed every check available without real elevation, and failed
  live. Only a real elevated session proves this class of Windows
  integrity-level behaviour -- see `AGP-13`-adjacent entries in the
  DepthWorks `ideations` repo for the general pattern.
- **When you can't get definitive proof of root cause, instrument the
  actual code path for next time rather than keep arguing from one
  inconclusive data point.** The operator was right to push back on the
  "it's the sandbox" conclusion after just one PowerShell test; building
  `6lg`'s diagnostic was the correct response, not defending the prior
  theory further.
- **A report's symptom is evidence; its implied mechanism is a guess** --
  reinforced a fourth time this session by the GPU-icons report above,
  which is being deliberately left uninvestigated rather than guessed at
  cold.
