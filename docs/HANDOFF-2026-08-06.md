## 2026-08-07, part 6: network attribution (`vanish-uninstaller-bfh.1`)

First piece of Stage 15, built to the corrected order recorded on `bfh`: a
Health Advisor section that reaches a VERDICT about the network, with zero
network I/O. `INV-4` is untouched and `test/network-verify.ps1` asserts it by
name, including `Test-NetConnection` and `Test-Connection` individually --
those are the two an author reaches for first when adding "is the internet up",
so removing the assertion is now a deliberate act.

The verdict that matters is the negative one: "nothing on this PC is using the
network", which sends the reader to their router instead of leaving them
clicking around the app. It is reachable locally because it is a claim about
local state.

**What it refuses to do**: per-program byte rates. Windows does not attribute
bytes to a process without an ETW kernel trace, so a per-app number here would
be fiction. The panel reports connections held and peers, states why on screen,
and the harness fails any row matching a rate pattern or any marketing string
from the banned list on `bfh`.

**Sources were measured, not assumed**: .NET `GetIPStatistics` (44ms) and
`netstat -ano` (40ms) over `Get-NetAdapter` (2.5s) and `Get-NetTCPConnection`
(1.3s) -- the engine spawns a fresh powershell per action, so module autoload
is paid every call, not once.

**Two bugs worth remembering**:

- The peer count read 1 for every program. The variable was called `$host` -- a
  PowerShell automatic variable. The assignment silently did nothing and every
  connection shared one hashtable key. It looked plausible on screen.
- Windows 11 gates Wi-Fi signal behind Location permission AND elevation, and
  `Get-BitsTransfer -AllUsers` needs elevation. Both degrade to "unknown" with
  the reason, never to "none" (Rule 24).

**Separately, an icon audit**: five `fa-*` classes referenced by the UI were
never defined in `assets/icons.css`, including `fa-lightbulb` on every orphaned
startup row. An undefined icon is a blank square -- nothing throws, nothing
logs, and no DOM test catches it because the element is present and correctly
sized. Drawn now, and `test/icon-verify.js` diffs referenced against defined.

`npm test` 361/0 unelevated, `npm run verify` green.

## 2026-08-07, part 4: left-over Store app data sweep (`vanish-uninstaller-udu`)

Operator asked for the UWP idea; the shape chosen, of three offered, was the
leftover sweep rather than shipping Vanish itself as an MSIX.

Uninstalling a Store app leaves `%LOCALAPPDATA%\Packages\<PackageFamilyName>`
behind forever. Nothing in Windows collects it and nothing in Vanish could see
it -- the app list reports packages Windows still registers, which is exactly
the set these folders are not in. New seventh System Clean cleaner
(`Find-UwpLeftovers`, cleaner id `uwp-leftovers`). On the dev machine: 24 MB
belonging to a vendor utility removed long ago, scan 1.4s.

Every ambiguity resolves toward keeping the folder, because the failure mode
here is deleting the data of an app you still use:

- the "installed" set is the UNION of this user's registrations and, elevated,
  every user's (`Get-AppxPackage -AllUsers`);
- Windows' own shell/framework families are listed but never removable --
  servicing unregisters them briefly, so "looks orphaned" is not "is orphaned";
- folders touched in the last 7 days are held back entirely, and the sweep
  states how many, since an install in flight looks exactly like a leftover;
- `%LOCALAPPDATA%\Packages` is not a Store-only directory -- it holds every
  AppContainer profile, including sandboxes ordinary desktop programs create
  (Chrome's `cr.sb.*`, Windows' `ActiveSync`). Those never had a package, so
  "no package claims it" says nothing about them. Excluded by folder shape
  (`Name_<13-char publisher id>`); the first draft proposed nine of them.

Also here: registered packages whose install folder is gone, as audit-only
rows (that is why the Start tile does nothing), and the first **file**-kind
cleaner -- `cleaner-purge` gained a file branch, so folders move into the vault
whole. `test/phase4-ipc-verify.js` now drives that round trip end to end, which
is the first time any automated run has quarantined and restored a real file.

**Found on the way**: `Get-FolderSize` had never returned anything but 0.
`return if ($size) { $size } else { 0 }` is not the expression PowerShell 5.1
reads it as. It had no live callers at the time -- the app-list caller was
deleted for being slow in part 2 -- so nothing on screen was ever wrong, but
the next caller would have inherited a helper that silently agrees every folder
is empty. Fixed, plus `-Force` so hidden subtrees (where app data actually
lives) are counted.

`npm test` 328/0 unelevated, `npm run verify` 156/0. Elevated purge/restore of
a real Store leftover is section 3b of the sandbox checklist -- a human at the
console, same as everything else destructive.

## 2026-08-07, part 3: elevated-relaunch blank window (portable exe)

Operator ran the packaged portable exe, clicked "Restart as administrator",
got a correctly-sized, correctly-coloured window with no content painted in
it. Real bug, portable-build-specific: `attemptElevatedRelaunch` (`main.js`)
relaunched `process.execPath`, which for a portable build is a temp-extracted
copy that the original instance's exit can race-delete out from under the new
elevated process reading it. Fixed by preferring
`process.env.PORTABLE_EXECUTABLE_FILE` (electron-builder sets this to the
stable exe path specifically for this case) with `process.execPath` as
fallback for the installed/dev case. Added `show:false` + `ready-to-show` +
`did-fail-load` so a future failure of this kind surfaces a real dialog
instead of a silent blank window. Commit `e00f252`.

**Cannot be verified by any automated harness** -- it is a live UAC path, needs
a human at the console. Filed as `vanish-uninstaller-jhh` (P0). The Windows
Sandbox checklist now has a section 0 specifically for this
(`test/sandbox/VERIFICATION-CHECKLIST.md`), ahead of the pre-existing `69a`
item, because `69a` tests `npm start` against source and never exercises
`PORTABLE_EXECUTABLE_FILE` at all -- only the packaged exe does.
`test/sandbox/sandbox-setup.ps1` now prints whether a packaged build is
present in `dist\` and how fresh, so the human doesn't start the checklist
against a stale or missing build.

first, record the result on `jhh`.

## What actually happened

Prior sessions fixed defects one at a time, each time the operator
reported one. Each individual fix was real, tested, and verified. The
aggregate result was still a broken product, for two compounding reasons:

**1. Fixture-shaped testing validated fixture-shaped reality.** Every UI
test in this repo runs against `test/fixtures/stub-preload.js`: one fake
app, clean well-formed fields, instant responses. The real machine has
163 apps of varied shape, multi-second scans, partial states, Windows
component entries, and a scrollbar. The suite reported 312/312 passing
while the app was visibly broken on screen. Most damning specific case:
`test/ui-interaction-verify.js` exists *specifically* to catch buttons
that render but cannot be clicked (its own header documents a prior
occlusion defect) -- and it passes green while real action buttons in the
uninstall wizard sit occluded on the operator's screen.

**2. New scope was added on top of a foundation that did not hold.**
This same session scoped three new roadmap stages (15 bandwidth panel,
16 firewall sweep, 17 Windows Update rollback) plus assorted re-scoping
work, while the already-shipped surfaces were substantially non-functional.
The scoping was individually defensible. The sequencing was indefensible.

Both failure modes are already documented as general patterns in
`D:\Depthworks\Projects\ideations\agent-verification-pitfalls\RETROSPECTIVE.md`
(AGP-1 especially). They were written down twice during this session and
still not applied where it mattered. Read that file before doing
diagnostic or verification work here.
